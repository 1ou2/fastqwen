## Overnight pilot

The [launcher](../scripts/run_sft_night.sh) defaults to a capped **2,000-step**,
single-GPU EN/FR/code pilot, with batch size 1 and accumulation 4. This processes
roughly 8,000 examples, not a full epoch over the available data. Requested source
groups retain natural row proportions among length-eligible records, without
balancing. The pilot is exploratory; mixture optimization and tool data remain
future work.

The launcher uses GPU 2, requires 60,000 MiB free GPU memory and 100 GiB free disk,
refuses existing output/log/status paths, and never stops containers itself.
CPU tokenization runs first and may leave the GPU idle during preparation. Its
full-corpus duration has not been measured. The launcher records a sibling log
and process exit-status file; the trainer writes `training-manifest.json`.

After explicitly choosing to launch, run from the repository root:

```bash
tmux new-session -d -s sft-pilot-20261104 \
  bash scripts/run_sft_night.sh data/runs/sft-pilot-20261104
```

This survives SSH disconnection. Monitor with:

```bash
tail -n 40 data/runs/sft-pilot-20261104.log
tmux attach -t sft-pilot-20261104
```

Checkpoints are saved every 100 updates, retaining up to three; validation runs
every 200 updates with up to 64 length-eligible examples per source group. Final
model/tokenizer export occurs on successful completion. Inputs, tokenized files,
and implementation source are hashed; source snapshots are copied into the run
so the Spark backup includes the implementation alongside the checkpoint.

For an interrupted run, choose a complete checkpoint and use the identical
settings and output directory, adding `--resume-from`. Do not rerun the fresh-run
launcher against an existing run, change world size, or alter the hashed source
files. For example, only if checkpoint 100 actually exists and is complete:

```bash
CUDA_VISIBLE_DEVICES=2 .venv/bin/python -u scripts/train_draft.py \
  --qa-dir data/runs/qa-export-20261104-v1 \
  --output-dir data/runs/sft-pilot-20261104 \
  --group s1-en --group s1-fr --group s2-code \
  --max-length 2048 --gradient-accumulation 4 --max-steps 2000 \
  --eval-per-group 64 --save-steps 100 --eval-steps 200 \
  --resume-from data/runs/sft-pilot-20261104/checkpoint-100
```

## Timing and limits

The longer smoke took about 29 seconds for its first two updates and 24 seconds
for its resumed two updates, with a checkpoint written every update. These tiny
runs include startup/evaluation/IO effects and are not a steady-state throughput
measurement. Re-estimate runtime from the first 50-100 pilot updates, separately
from CPU preparation. No 6-10-hour completion promise or four-GPU speedup is made.

Hybrid-attention training currently uses correct but slower PyTorch fallbacks:
`causal_conv1d` and `flash-linear-attention` are not installed. Do not change native
kernels or packages mid-run; any optimized stack needs its own smoke. No
distributed SFT has been validated, and this entry point refuses `WORLD_SIZE > 1`.
Finite-metric checks stop the run on logged non-finite loss/gradient metrics.

Before releasing the cluster, verify the final Spark backup. Offline draft
acceptance, quality grading, and Spark speculative comparisons remain separate
gates; a saved checkpoint alone does not establish success.
